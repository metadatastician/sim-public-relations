= PR Practice Lab — How It Works
:toc: left
:icons: font
:reproducible:

[.lead]
This document connects PR Practice Lab's product claims to the implementation
and records where the present implementation stops. It describes the Phase A
vertical slice; it is not a claim that the complete learner product exists.

== Product boundary

PR Practice Lab is fictional professional-learning software for practising
public-relations and communications judgement. It does not provide employment,
placement hours, live client work, a professional qualification, accredited
CPD, or a guarantee of competence or employment. The authoritative product
boundary is stated in `docs/foundation/foundation-spec-v0.1.adoc` and repeated
inside the scenario manifest and native kernel.

The first scenario, `northstar-mobility-001`, places a learner in a bounded
junior agency role supporting the fictional launch of an accessible community
transport pilot. All organisations, people, publications, contacts and
messages in that scenario are fictional.

== Epistemic model

The simulator keeps five kinds of knowledge separate:

. *Authored reality* — immutable fictional history and response conditions.
. *Potential evidence* — material that exists but may never be requested.
. *Disclosed record* — exactly what was available to the learner at a logical
  point in the run.
. *Learner model* — interpretations, assumptions, uncertainties, plans and
  artefacts produced from the disclosed record.
. *Normative model* — provisional professional rules, approvals and assessment
  interpretations.

This separation prevents hindsight scoring and keeps an approved organisational
message from being mistaken for an established fact. The architecture and trust
boundaries are specified in `docs/architecture/system-architecture.adoc`.

== Scenario packaging and hidden reality

Scenario material lives under `scenarios/northstar-mobility-001/`:

* `manifest/public.a2ml` identifies learner-visible scenario metadata;
* `evidence/` contains the incomplete brief and requestable fictional evidence;
* `tasks/` declares concurrent workstreams and plural defensible routes;
* `assessment/rubric-map.a2ml` maps observable events to provisional rubric
  dimensions without equating outcome with competence;
* `fixtures/golden-runs.a2ml` declares expected routes and adverse cases; and
* `reality/reality.a2ml` contains trusted authored reality that must never be
  delivered to a learner client or learner-controlled AI.

`tools/validate-scenario.sh` checks identities, required material, claim
boundaries, plural routes and native/source alignment. It derives a non-empty
deny list from authored reality and scans learner-side source material for exact
scenario-specific leak tokens.

`tools/test-scenario-boundary.sh` proves that validator is not vacuously green.
It requires a clean copy to pass and plants three defects that must fail: a
hidden-truth leak, an empty derived deny list and a scenario falsely represented
as employment experience.

This source-side gate is deliberately narrow. Packaged artefacts, compiled
binaries, runtime channels, AI prompts and timing side channels are not yet
covered; that gap is recorded in `docs/KNOWN-DEBT.adoc`.

== Deterministic native kernel

`src/practice.zig` is the trusted Phase A event/replay kernel. Commands become
authoritative only after their preconditions are checked and their events are
appended. The kernel models evidence requests, uncertainty, objectives,
stakeholders, drafting, verification, accessibility, approval, enquiry
handling, route choice, campaign consequences and assessment observations.

`src/main.zig` provides a small command-line projection. It can show the Phase A
home screen, replay one named route, or replay all implemented golden routes:

[source,sh]
----
zig build run -- demo corrected
zig build run -- demo staged
zig build run -- demo pause
zig build run -- demo critical
zig build run -- golden
----

Each replay reports the route, threshold result, critical-error state, event
count, campaign consequence measures and deterministic digest. A favourable
campaign outcome does not substitute for competent reasoning, and a critical
integrity error cannot be averaged away by polished work elsewhere.

The CLI is an executable replay and assessment slice, not yet an interactive
learner interface. There is no inbox UI, persistent run store, facilitator
view, hosted service or evidence-passport export.

== Assessment model

The assessed unit is a traceable professional act:

----
available evidence -> interpretation + uncertainty -> objective and audience
-> considered options -> approved action -> response -> adaptation -> reflection
----

`docs/assessment/competency-framework.adoc` defines observable capabilities.
`docs/assessment/rubric-v0.1.adoc` and the scenario rubric map connect those
capabilities to recorded events. `docs/assessment/validity-limitations.adoc`
states what a run can and cannot support.

The professional reference pack is `PROVISIONAL/UNREVIEWED`. No CIPR, PRCA,
AMEC, employer, educator, accessibility specialist or independent practitioner
has approved the rubric or scenario. The implementation therefore rejects
authoritative scoring and makes no accreditation or qualification claim.

== AI boundary

AI is treated as part of the professional situation, not as an authoritative
assessor. A task may prohibit, permit or require AI assistance. Permitted use
must be declared and verified, and the learner remains accountable for the
result. AI output is not evidence.

No external AI service is required by the reference implementation. Hidden
reality, response logic, rubric interpretations and model routes must never be
sent to a learner-controlled model.

== Verification

The Phase A executable and boundary checks are:

[source,sh]
----
zig build test
zig build run -- golden
bash tools/validate-scenario.sh
bash tools/test-scenario-boundary.sh
----

Passing these establishes only what those instruments cover: the current Zig
kernel tests, deterministic golden replay, source-side scenario structure and
the three planted boundary failures. It does not establish accessibility
conformance, professional validity, learner efficacy, deployment readiness or
security of a future interactive product.

== Design lineage

The epistemic and assessment structure is adapted from
`metadatastician/sim-insolvency`: immutable authored reality, monotonic
disclosure, beliefs distinct from facts, append-only events, plural defensible
routes, competence separate from consequence and post-submission reveal. The
professional content and progression model here are specific to public
relations and communications practice.
